# Policy assistant — build and release plan

## 1. User → problem → value

Customers need understandable returns/exchanges guidance without hunting through
policy clauses. One Flash agent explains retrieved evidence; ordinary software
controls sources, dates and displayed citations. The product guides customers,
but does not execute refunds, exchanges or support requests.

## 2. Architecture built

See the [README diagram](../README.md#6-agent-and-system-design).
The local gateway executes current source, not the old deployed multi-agent code.

| Component | Decision | Tradeoff |
|---|---|---|
| Model | One Gemini 3.8 Flash response after retrieval | Lower serial overhead; quality still needs evaluation |
| Scope | Local rules, repeated in the prompt | Cheap and predictable for known wording; incomplete semantic coverage |
| Evidence | Fresh RAG, returns policy + catalogue whitelist | Network dependency; honest failure when unavailable |
| Citations | IDs validated against current evidence; links generated by code | Identity is verified, not whether the text entails the answer |
| Conversation | Managed session history; optional local SQLite | Continuity without Firestore |
| Memory | Selected order/item/issue details; two-second recall and three-second write budgets | Optional recall can fail or be eventually consistent |
| UX | Complete validated answer over SSE | No unchecked token streaming; time-to-first-text equals generation time |
| Actions | No action tools, billing agent or reviewer routes | Customer must take their own next step |

## 4. Evaluation and release gates

These are goals, not measured results:

| Outcome | Gate |
|---|---|
| Supported policy answer | ≥90% held-out accuracy |
| Critical domain/action boundary | 100% tested critical refusals |
| Citation identity | 100% map to actual retrieved evidence |
| Semantic citation support | Judge + human review, separate from identity |
| Customer isolation | Zero tested cross-customer leaks |
| Useful cross-session recall | ≥90% relevant recall success |
| Completed latency | Representative p95 ≤8s |
| Capability honesty | No executed-action claims |

Start evals with a rubric and human-scored good/poor/borderline examples. Hide
labels from the judge, inspect false passes, and calibrate on a separate holdout.
Then score fresh Flash outputs. Preserve the old datasets as historical evidence,
not new-design acceptance coverage.

## 5. Release order

1. Verify the local customer path, managed state/recall and trace privacy.
2. Run calibrated evaluations, representative latency/cost checks and abuse cases.
3. Obtain approval to deploy; validate the new cloud customer path.
4. Inventory legacy resources and prepare rollback.
5. Obtain approval before retiring Firestore or reviewer cloud services.

Git retains the earlier implementation. A source rollback does not justify
restoring an unsafe customer workflow; use a known-good release with clear scope.

## 6. Product limitations

Keyword rules are not a complete semantic firewall. Prompt-injection resilience,
mixed intents, conflicting evidence and memory isolation need held-out testing.
Policy PDFs are fictional demonstration documents, not legal advice.
Anonymous browser identity does not verify order ownership. Consent, deletion,
retention, distributed rate limiting and public hosting remain release work.
